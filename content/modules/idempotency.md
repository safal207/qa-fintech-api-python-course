# Идемпотентность, retry и timeout в платёжном API

Endpoint: POST /payments

## Цели обучения

- различать безопасный retry и повторное создание платежа
- проверять, что одинаковый Idempotency-Key возвращает тот же результат операции
- выявлять двойное списание после клиентского timeout

## Сценарий

Клиент отправил платёж на 1000 TRY. Сервер успел создать операцию и изменить баланс, но клиент не получил ответ из-за timeout. Клиент повторяет запрос с тем же Idempotency-Key.

## Инварианты

- повтор с тем же Idempotency-Key не создаёт новую платёжную операцию
- идентификатор платежа при повторе совпадает с идентификатором первой операции
- итоговое списание и комиссия применяются только один раз
- ответ на повторный запрос не скрывает фактический статус уже созданной операции

## Эталонные тезисы

- Retry безопасен только тогда, когда повтор не меняет бизнес-результат уже принятой операции.
- Один Idempotency-Key должен быть связан с одним сохранённым результатом и одним идентификатором платежа.
- После timeout QA проверяет не только HTTP-ответ, но также число операций, баланс, комиссию и итоговый статус.
